# tidy

Use this skill when a task is finished and its notes need to be put in order. It reads the
notes, groups them by file and writes one short summary for the person who asked for the task.

## Before you start

- Read the ticket before anything else, so the notes are judged against what was asked.
- Do not ask a question that the ticket already answers. Look the answer up first.

## While you work

- Name every file the task changed, and the line of the change.
- Mark every guess as a guess. Start the sentence with the word "guess".
- Ask for a review after every small edit, however small, before the next edit.
- Stop at the first failing check and report it before anything else.

## What to write down

- Say which parts were not looked at. A reader should never have to guess which part is unchecked.
- Keep each reply under 40 lines.
- List the open items last.

## Closing

- End every reply with a table that sums up the changes, one row for each file.

## Why these steps

The notes of a finished task are read later, often by someone who was not there. Each step above
exists so that this reader can trust what is written without repeating the work. A reply that
names its files lets the reader go straight to the change. A reply that marks its guesses lets
the reader decide which parts to check again. A reply that says what was not looked at keeps the
reader from assuming more than was done. Short replies are read to the end; long ones are skimmed,
and a skimmed reply hides the one line that mattered. For the same reason the open items come
last: they are the first thing the next person needs, and the last thing they should be able to
miss. When a check fails, the reader wants the failure before the summary, because the summary of
a failed task is mostly noise.
